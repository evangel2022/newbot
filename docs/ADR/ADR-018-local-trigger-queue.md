# ADR-018: Local Trigger Delivery Queue

- Status: Accepted
- Date: 2026-10-05
- Supersedes: none

## Context

`docs/architecture.md` gives the scheduler "timers, heartbeat tasks, and session-bound external
triggers", and the ROADMAP Phase 4 exit criteria require that "an at-least-once trigger is
deduplicated by consumers and a failed delivery is marked failed, not retried forever".
nanobot's `docs/automations.md` specifies the shape: `/trigger <name>` creates a trigger bound to
the topic it was created from; `nanobot trigger <id> "message"` (or stdin) writes the message to a
durable workspace queue; the gateway consumes it; delivery is at-least-once, not exactly-once; a
delivery claimed but not finished before a restart is requeued; and if the turn fails, the
delivery is marked failed instead of retried forever. One gateway consumer runs per workspace.

## Decision

Local triggers are config-declared and delivered through a durable, per-delivery queue.

- Configuration adds `[triggers]` (`dir`, `pollIntervalSeconds`, default 1.0) and
  `[[triggers.items]]` entries of `{id, conversation}`; ids must be unique. Declaring triggers in
  config rather than creating them from a topic matches ADR-014 and newbot's config-first,
  fail-fast design, and is a deliberate difference from nanobot's `/trigger` command.
- `newbot trigger <id> [message]` resolves the id in the loaded config and enqueues one delivery;
  the message may be piped on stdin. An unknown id or an empty message is a usage error (exit 2).
- `TriggerQueue` (`adapters/stores/trigger_queue.py`) owns one JSON file per delivery under
  `triggers.dir` (default `<config dir>/triggers`, outside the agent workspace), written
  atomically. Deliveries move `pending → running → done|failed`. `enqueue` is deduplicated by
  delivery id (an existing file is not rewritten); `claim` returns pending deliveries plus any
  delivery left `running` by a crash (at-least-once redelivery) and marks them `running`;
  `done`/`failed` are terminal and are never claimed again (consumer deduplication). A file that
  cannot be parsed is quarantined as `*.invalid` so it cannot hot-loop the poll.
- `TriggerConsumer` (`app/triggers.py`) claims, submits each delivery through the hub into its
  bound conversation on the host transport, and marks the delivery done on success, failed on a
  deliberate submission error or a failed turn. `run_serve` registers the consumer on the
  scheduler only when triggers are configured.
- `InboundHandler`/`EventHub.submit` now return the turn's `TurnStatus` (with a new
  `TurnStatus.FAILED`) so a caller can tell a completed turn from a failed one without subscribing
  to events. The workbench ignores the returned value.

## Consequences

**Positive**

- Trigger delivery is durable (a message enqueued while the host is down waits), at-least-once,
  and deduplicated by delivery id; a failed delivery is terminal.
- Delivery reuses the hub and turn engine, so it inherits per-session serialization and the
  cross-session bound rather than adding a second execution path.
- The `TurnStatus` return lets scheduled turns and trigger deliveries report a failed turn without
  an event subscription.

**Negative / accepted costs**

- The registry is config-declared; there is no runtime `/trigger` creation or management view.
- The queue is polled, so delivery latency is up to `pollIntervalSeconds`, and it is a
  single-consumer queue (one host per `triggers.dir`), not a distributed queue.
- Delivery ids are generated by the CLI; an external system that wants its own idempotency key
  must pass one, which the CLI does not yet expose.
- The queue lives in the config directory rather than the agent workspace, so triggers are not
  agent-readable (a deliberate difference from nanobot).

## Alternatives considered

- **A workbench HTTP trigger endpoint.** Rejected: nanobot documents no public webhook receiver,
  and it would add a mutation surface a local CLI already covers.
- **Runtime trigger creation via `/trigger`.** Deferred: it needs a chat/topic surface newbot does
  not have; config declaration covers the delivery contract now.
- **An in-memory queue.** Rejected: a trigger enqueued while the host is down must survive, which
  is the point of a local trigger.
- **Exactly-once delivery.** Rejected: nanobot documents at-least-once; exactly-once would need a
  transactional store.
- **Reusing `POST /messages`.** Rejected: messages are immediate and unaudited; triggers need
  durability, deduplication, and terminal marking.
